# 开发路线图

## 目标

本文档给出本项目从环境准备到真机小规模测试的分阶段路线图。

总原则：

- 所有阶段都服从固定环境约束
- 先单机，再多机
- 先 SITL，再上板，再真机
- 先状态可见，再控制闭环，再任务智能
- 任何真机能力都必须先在 SITL 验证

## 总览

| Phase | 阶段名称 | 重点目标 |
|---|---|---|
| Phase 0 | 环境准备 | 固定版本环境与基础文档、脚本、网络约束明确 |
| Phase 1 | 单机 PX4 SITL + ROS2 通信 | 打通单机 PX4 与 ROS2 的基础链路 |
| Phase 2 | 多机 PX4 SITL | 实现多机实例、独立 namespace 和状态汇总 |
| Phase 3 | 基础起飞、降落、航点控制 | 建立基础飞行任务能力 |
| Phase 4 | leader-follower 编队 | 建立多机编队控制闭环 |
| Phase 5 | 任务分配和区域覆盖搜索 | 建立群体任务层和搜索能力 |
| Phase 6 | RK3588 部署 | 将核心能力迁移到机载伴随计算机 |
| Phase 7 | 真机小规模测试 | 进行小规模真机验证 |

## Phase 0：环境准备

### 目标

- 固定并验证当前开发环境
- 明确 WSL2、PX4、ROS2、QGC 的网络边界
- 建立文档与脚本骨架

### 核心任务

- 核对以下固定环境：
  - `PX4 v1.14.4`
  - `ROS2 Humble`
  - `Gazebo Classic 11.10.2`
  - `MicroXRCEAgent 2.4.1`
  - `WSL2 Ubuntu 22.04`
- 明确 `PX4_DIR` 与 `MICRO_XRCE_DDS_AGENT_DIR`
- 建立项目文档框架
- 明确多机 SITL、QGC、ROS2 的端口规划原则
- 准备启动脚本骨架：
  - `setup_env.sh`
  - `start_px4_single_sitl.sh`
  - `start_px4_multi_sitl.sh`
  - `start_micro_xrce_agent.sh`

### 阶段交付物

- `docs/environment.md`
- `docs/reference_analysis.md`
- `docs/architecture.md`
- `docs/roadmap.md`
- 环境变量与目录约定

### 验收标准

- 当前固定版本全部确认
- 外部依赖路径明确
- 不引入 ROS1 主线依赖
- WSL2/QGC 网络约束已形成文档

### 风险点

- WSL2 和 Windows Host 间 UDP 联通细节不清
- 后续若早期忽略端口规划，多机阶段会反复返工

## Phase 1：单机 PX4 SITL + ROS2 通信

### 目标

- 跑通单机 PX4 SITL
- 打通 PX4 与 ROS2 的基础消息链路
- 形成单机 `px4_bridge` 基础能力

### 核心任务

- 启动单机 PX4 SITL
- 启动 `MicroXRCEAgent`
- 在 ROS2 中订阅关键 PX4 状态话题
- 完成单机 namespace 方案验证
- 输出归一化单机状态消息
- 验证 offboard 进入前的消息时序

### 阶段交付物

- 单机 SITL 启动流程文档
- 单机 ROS2 通信链路说明
- `px4_bridge` 设计稿
- 关键话题清单

### 验收标准

- ROS2 能稳定读到单机 PX4 状态
- 能完成基础 arm/offboard 前置链路验证
- 不依赖 QGC 才能看到核心状态

### 风险点

- `px4_msgs` 与当前 PX4 版本匹配问题
- Micro XRCE-DDS 配置细节不稳定

## Phase 2：多机 PX4 SITL

### 目标

- 支持多机 PX4 SITL 并行运行
- 每架无人机具备独立 namespace
- 建立集群状态汇总能力

### 核心任务

- 设计多机实例 ID、system ID、namespace 映射关系
- 设计多机 SITL 启动脚本
- 设计多机端口与网络规划
- 为每架无人机启动独立 `px4_bridge`
- 实现 `swarm_manager` 的基础状态汇总能力

### 阶段交付物

- 多机 SITL 启动方案
- namespace 规范
- 集群状态数据模型
- 多机网络与端口文档

### 验收标准

- 至少 3 架无人机可同时运行 SITL
- 每架无人机状态在 ROS2 中可独立识别
- `swarm_manager` 能输出统一 fleet 视图

### 风险点

- 多机端口冲突
- PX4 与 ROS2 namespace 对齐不稳定
- QGC 在多机场景下的连接策略未提前规划

## Phase 3：基础起飞、降落、航点控制

### 目标

- 建立单机与多机基础飞行任务能力
- 完成起飞、悬停、降落、航点控制的任务化封装

### 核心任务

- 设计 `mission_manager` 基础状态机
- 封装基础动作：
  - takeoff
  - hold
  - goto
  - land
  - RTL
- 明确 PX4 控制模式切换顺序
- 支持基于航点文件或简单路径的任务执行

### 阶段交付物

- 基础动作接口定义
- 基础任务状态机文档
- 单机/多机基础任务演示流程

### 验收标准

- 单机可稳定完成起飞、悬停、降落
- 单机可执行简单航点任务
- 多机可分别接收独立基础任务

### 风险点

- offboard 指令中断后的降级策略
- 航点控制与 PX4 内部模式协同问题

## Phase 4：leader-follower 编队

### 目标

- 建立 leader-follower 编队控制主线
- 支持基础多机相对队形保持

### 核心任务

- 设计 leader / follower 角色模型
- 设计编队配置与偏置表达方式
- 设计邻居拓扑与状态流
- 实现 `formation_controller`
- 将编队任务纳入 `mission_manager`
- 设计 leader 丢失和 follower 降级策略

### 阶段交付物

- 编队控制数据流文档
- 编队配置格式
- 编队状态可视化基础接口

### 验收标准

- 至少 3 架无人机可完成基础编队起飞和跟随
- leader 执行简单轨迹时 follower 可维持预定相对位置
- 编队中断后可安全退出到 hold / land / RTL

### 风险点

- 相对控制坐标系选择不一致
- 多机时延和状态延迟导致编队抖动
- 无碰撞保护时编队测试风险较高

## Phase 5：任务分配和区域覆盖搜索

### 目标

- 建立群体任务层
- 让多机具备区域搜索与任务分配能力

### 核心任务

- 设计 `task_allocator`
- 设计 `coverage_planner`
- 引入覆盖路径生成算法原型
- 将搜索区域切分为多机可执行子任务
- 支持任务进度上报与状态可视化
- 为后续目标检测和雷达感知预留任务输入接口

### 阶段交付物

- 区域覆盖任务模型
- 任务分配策略文档
- 覆盖搜索规划文档
- 搜索任务进度接口定义

### 验收标准

- 给定一个搜索区域后，可自动生成多机分区任务
- 多架无人机可执行各自区域搜索路径
- `swarm_manager` 或地面侧可看到整体任务进度

### 风险点

- 算法原型到工程化落地差距较大
- 搜索任务与编队任务共存时需要任务仲裁

## Phase 6：RK3588 部署

### 目标

- 将核心能力迁移到 `RK3588` 伴随计算机
- 建立机载运行、启动和维护方式

### 核心任务

- 明确 RK3588 系统环境
- 规划机载 ROS2 工作区安装方式
- 设计 `onboard/rk3588_setup/` 脚本
- 设计 `systemd` 启动方式
- 验证机载 `px4_bridge`、状态发布、基础任务执行
- 评估 CPU、内存、网络带宽占用
- 为感知模块选择非 NVIDIA 绑定的推理路径

### 阶段交付物

- RK3588 部署文档
- 机载启动脚本
- `systemd` 服务模板
- 资源占用与性能测试记录

### 验收标准

- RK3588 上可运行核心 ROS2 节点
- 能与 PX4 飞控稳定通信
- 能完成基础状态上传与简单任务执行

### 风险点

- RK3588 驱动与依赖兼容性
- 感知推理框架选型不当导致后续返工
- 真机网络与 WSL2 仿真网络模型差异较大

## Phase 7：真机小规模测试

### 目标

- 在小规模真机环境验证主线能力
- 从单机到多机逐步开放测试范围

### 核心任务

- 制定飞行测试清单与风险控制流程
- 明确人工接管、地理围栏、失联保护策略
- 先做单机真机验证：
  - 状态通信
  - 起飞/悬停/降落
  - 简单航点
- 再做小规模多机验证：
  - 状态共享
  - 基础编队
  - 简化搜索任务

### 阶段交付物

- 真机测试方案
- 安全检查清单
- 测试日志与问题清单
- 真机参数与部署记录

### 验收标准

- 单机真机稳定完成基础动作
- 小规模多机完成基础状态共享和简化编队
- 关键异常场景可安全退出

### 风险点

- 真机环境中的 GNSS、磁罗盘、无线链路与仿真差异
- 多机通信不稳定导致编队和任务逻辑失效
- 若没有严格分阶段测试，风险会迅速放大

## 跨阶段共性要求

以下内容应贯穿所有阶段：

- 文档持续更新
- 统一命名规范
- 参数与配置文件外置
- 日志记录与问题留痕
- 每完成一阶段后再进入下一阶段

## 推荐推进顺序

建议严格按顺序推进：

1. 先完成 `Phase 0`
2. 再打通 `Phase 1`
3. 之后再做 `Phase 2`
4. 编队控制必须在 `Phase 3` 稳定后再进入 `Phase 4`
5. 任务分配与覆盖搜索必须在多机控制稳定后再进入 `Phase 5`
6. `RK3588` 部署与真机测试必须建立在前面 SITL 验证完成的基础上

## 结论

本路线图强调：

- 先把 `ROS2 + PX4` 基础链路做稳
- 再把多机状态和控制闭环做稳
- 再进入编队、任务分配和覆盖搜索
- 最后再做 `RK3588` 部署和真机验证

这条路线最符合当前项目约束，也最适合控制开发风险。
